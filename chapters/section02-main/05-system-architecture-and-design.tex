\chapter{System Architecture}
\label{chap:system_architecture}

This chapter presents the architecture of \gls{SafeVision} and explains how the main system components are organized to support detection, redaction, user interaction, and deployment. It further describes the relationship between the system components and the deployment structure used to make the application available.

\section{System Architecture Overview}
\label{sec:system_architecture_overview}

The system is designed as a modular client-server architecture for detecting and redacting sensitive content in visual media. At a high level, the architecture consists of a frontend, a backend/\acrfull{api} layer, and separate processing components for detection and redaction. Figure~\ref{fig:system_architecture_overview} provides an overview of the main architectural elements and their relationships. The following subsections describe the design principles and system components in more detail.

\methodheading{Architectural Design}
\label{architecture_design}

The system follows a layered architectural design, where each layer has a specific responsibility and communicates with adjacent layers. This design reduces system complexity and enables independent development of components \cite{shaw1996software}. It also simplifies debugging and testing, as each layer can be evaluated in isolation.

\begin{itemize}
    \item \textbf{Presentation Layer (Frontend):} Handles user interaction and displays results.
    \item \textbf{Application Layer (Backend):} Manages requests and coordinates processing.
    \item \textbf{Processing Layer (Backend):} Performs detection and redaction operations.
\end{itemize}

\methodheading{Design Principles}
\label{design_principles}

Several of the qualities introduced earlier as non-functional requirements in Section~\ref{sec:nfr} also influenced the architectural design of \gls{SafeVision}. In this section, these themes are revisited from a design perspective in order to show how they shaped the overall system structure. Table~\ref{tab:design_principles} summarizes the main design principles considered in the architecture.

\begin{table}[H]
\centering
\begin{tabular}{|p{5cm}|p{9cm}|}
\hline
\textbf{Design Principle} & \textbf{Description} \\ \hline

\textbf{Client--Server Separation} & 
The system separates user interaction from processing logic by placing the \acrshort{ui} in the client and computational tasks in the server backend. This allows \acrshort{ml} \gls{inference} and other processing-heavy operations to be handled outside the frontend. \\ \hline

\textbf{Separation of Concerns} & 
The system assigns distinct responsibilities to different components. In particular, detection and redaction are implemented as separate modules, which reduces coupling and makes the pipeline easier to maintain and extend. \\ \hline

\textbf{Modularity} & 
The architecture is designed so that individual components can be replaced or improved without requiring major changes to the rest of the system. This is especially relevant for detection models, which may need to be updated over time. \\ \hline

\textbf{Stateless Backend Design} & 
The backend processes each request independently without relying on persistent session state. This simplifies deployment and supports scaling across multiple instances. \\ \hline

\textbf{Privacy by Design} & 
The system avoids unnecessary persistent storage of sensitive data in order to reduce exposure risk and align the architecture with data minimization principles. \\ \hline

\end{tabular}
\caption{Main design principles considered in the \gls{SafeVision} architecture}
\label{tab:design_principles}
\end{table}

Together, these principles reflect the main architectural priorities of \gls{SafeVision}. They were used to support scalability, maintainability, extensibility, and privacy-aware handling of sensitive visual data, while also keeping the system practical to develop and deploy within the constraints of the project.

\section{System Components}

Following the overview of the system architecture, this section presents \gls{SafeVision} in terms of its main functional components and their responsibilities. The system consists of four primary components: the \acrshort{ui}, the Detection component, the Redaction component, and the \acrshort{api} layer. Together, these components illustrate how the system distributes responsibility across interaction, processing, and communication layers.

\methodheading{User Interface}

The \acrshort{ui} is a web-based frontend that serves as the primary point of interaction between the user and the \gls{SafeVision} processing pipeline. It is responsible for presenting detection results, supporting user interaction, and maintaining a consistent interaction state as results are reviewed and redaction is applied. A central element of the UI is the workspace, which offers an interactive view of uploaded images or videos and the corresponding detected regions, enabling users to inspect and adjust detections before proceeding. In this way, the UI supports a hybrid workflow, as further discussed in Chapter~\ref{user_interface_and_usability}. The UI communicates with the backend through the \acrshort{api} layer and also supports the privacy-oriented design described in Subsection~\ref{design_principles}.

\methodheading{Detection and Redaction Component}

A central backend processing component in the system is organized around two main workflows, detection and redaction. As illustrated in Figure~\ref{fig:api_workflows}, these pipelines follow the same overall structure for both still images and video. The main difference is that video processing operates across multiple frames, and the frame-level results must be accumulated before being returned to the frontend.

Figure~\ref{fig:api_workflows}(a) shows the high-level detection workflow. After input media is received by the \acrshort{api}, it is decoded and may optionally undergo
preprocessing. The media is then passed to multiple detection components, which can operate in parallel. Their outputs are subsequently normalized into a consistent format before being returned through the \acrshort{api} layer. For still images, this produces a direct detection result. For video, the same workflow is applied to relevant frames, and the frame-level detections are collected into a unified response.

Figure~\ref{fig:api_workflows}(b) shows the corresponding redaction workflow. During this stage, the backend receives the input media together with the validated detection results before applying the selected \gls{anonymization} method. Depending on the selected strategy, redaction may be based on \gls{bounding box}es or \gls{segmentation} masks. Redaction is applied directly to the image, while for video, the same workflow is applied frame by frame, after which the processed frames are recombined into the final redacted video. This design makes it possible to separate redaction from detection as two independent but connected stages.

\methodheading{\acrshort{api} Layer}

The \acrshort{api} layer provides the main communication interface between the frontend and backend. Through HTTP-based requests, it exposes detection and redaction functionality through well-defined endpoints, allowing the \acrshort{ui} to request processing without depending on the backend's internal implementation. Following the stateless and privacy-oriented design principles described in Subsection~\ref{subsec:architecture-principles}, the API is organized into dedicated controllers for different processing tasks. As shown in Figure~\ref{fig:backend-architecture}, this layer forms the entry point to the backend and forwards valid requests to the service layer.

The service layer is mainly used to manage shared backend resources. In \gls{SafeVision}, it ensures that \acrshort{ml} models are loaded once and reused throughout the application lifecycle instead of being initialized for every request. Keeping this responsibility separate from the \acrshort{api} routes reduces unnecessary loading overhead while preserving a clearer separation between request handling and model management.

\methodheading{\acrshort{ml} Development Process}

In addition to the deployed application components, the project included a separate development process for custom \acrshort{ml} models. This was necessary because the custom-trained models used in \gls{SafeVision} had to be prepared, trained, and evaluated before they could be integrated into the backend. As illustrated in Figure~\ref{fig:ml_pipeline}, this process begins with preparing datasets so they can be used consistently during training. The models are then trained and evaluated in a dedicated development environment, before selected model artifacts are moved into the \gls{SafeVision} backend for \gls{inference}.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=1.0\textheight,keepaspectratio]{figures/images/chapter-5/machine-learning-pipeline.png}
\caption{General \acrshort{ml} pipeline consisting of data preparation, model training, evaluation, and deployment phases (adapted from \cite{ml_pipeline_source}).}

Keeping this process separate reduced the coupling between experimental model development and the deployed application. The \gls{SafeVision} application handles workflows, while model development is carried out separately until the models are ready for integration. This made it possible to experiment with datasets and training configurations without affecting the production-oriented parts of the system. The tools, environments, and repository structure used for this process are described in Chapter~\ref{chap:technologies_and_methodologies}, while the concrete implementation of dataset preparation, training, and model integration is presented in Chapter~\ref{chap:implementation_details}.

\section{Deployment Architecture}

The deployment architecture describes how \gls{SafeVision} is made available as a web-based system during operation. As shown in Figure~\ref{fig:deployment_architecture}, the frontend and backend are deployed as separate components. This makes it possible to update or redeploy the backend without necessarily redeploying the frontend, and vice versa. The separation also keeps the \acrshort{ui} independent from the processing and \gls{inference} environment, which makes future maintenance and extension easier. Figure~\ref{fig:deployment_architecture} also includes the CI/CD flow used to support the deployment process. More specific technologies and infrastructure choices used to realize this deployment are described in Chapter~\ref{chap:technologies_and_methodologies}.
