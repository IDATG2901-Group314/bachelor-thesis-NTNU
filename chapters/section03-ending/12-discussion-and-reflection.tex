\chapter{Discussion and Reflection}
\label{chap:dar}

This chapter discusses the main outcomes of the \gls{SafeVision} project and reflects on the decisions that shaped the final system. It considers what the project achieved, where important limitations remain, and what lessons can be drawn from the development process. 

%------------------------- 12.1 -------------------------

\section{Achievement Assessment}

This section assesses how well the \gls{SafeVision} project fulfilled its intended purpose in relation to the final system that was developed. The assessment considers the original goals (Section~\ref{sec:goals}) the additions that went beyond the initial scope, and what these outcomes show about the strengths and limitations of the project.

\noindent\textbf{Main Goals Achieved}

The main goal of \gls{SafeVision} was to develop a system for detecting and anonymizing sensitive information in still images. This goal was achieved through a workflow where users can upload an image, run automatic detection, review the detected regions, and apply redaction. This demonstrates that the project succeeded in creating a complete workflow rather than only isolated detection or redaction components. Even though this goal was achieved, there is still room for further refinement in usability and interaction design as described from Section~\ref{sec:user-testing}.

The system detects several types of privacy-relevant visual content, including faces, visible text, license plates, people, vehicles, and other objects that may reveal sensitive information. This was important because the project’s understanding of sensitive information became broader than only direct identifiers. As discussed in Chapter~\ref{chap:theoretical_foundation}, visual media can also contain indirect identifiers and contextual details. In retrospect, this broader definition could have been established earlier in the project, since it would have helped guide dataset selection, model priorities, and evaluation criteria from the beginning.

Another important goal was to combine automation with user control. This was achieved through a workflow where users can review and modify detections before applying redaction. The design implications of this choice are discussed further in Section~\ref{sec:why_hybrid_user_review_was_retained}. This was one of the most important outcomes of the project, because it reflects the limitation of fully automatic redaction. The system can reduce repetitive manual work, but it still depends on user judgment when sensitivity is contextual or when detections are uncertain.

The project also achieved the goal of building a working technical architecture. The system was implemented with a React and TypeScript frontend, a Python FastAPI backend, and separate \acrshort{ml} components. The implications of this architecture for practical adoption was discussed further in Chapter~\ref{chap:implementation_details}. This architecture made it possible to connect upload, detection, review, redaction, and export into one system. However, it also showed that integrating several \acrshort{ml} components into an interactive workflow requires significant coordination between the system components.

Another important learning outcome was the experience of working with a product owner. Collaboration with Safe Media AI helped the group understand the importance of aligning technical development with stakeholder needs. For example, some functionality, such as \gls{inpainting}, was retained not only because of its technical relevance, but also because it was requested by the product owner. This gave the group practical insight into how agile development involves balancing technical quality, user value, project scope, and time limitations.

The project also provided experience in collaborating with a product owner. This contributed to a better understanding of agile development processes, particularly the importance of feedback, clarification of requirements, and prioritization of functionality. Input from the product owner helped guide decisions about which features were most important for the final system, and it encouraged the group to think beyond implementation alone. Instead of only considering whether a feature was technically possible, the group also had to consider whether it was useful, understandable, and relevant for the intended use case. 

The project also provided experience in collaborating with a product owner, which contributed to a better understanding of agile development processes. This collaboration highlighted the importance of feedback and development prioritization. As discussed in Section~\ref{sec:stakeholder-involvement-external-feedback}, feedback from Safe Media AI influenced several project decisions, especially in relation to video functionality, backtracking, and possible solutions for manual tracking. It also encouraged the group to consider not only whether a feature was technically possible, but whether it was useful, understandable, and relevant for the intended use case. At the same time, closer and more frequent involvement throughout the process could have helped validate technical choices earlier and reduce time spent on directions that were less important for the final system.

\noindent\textbf{Achievements Beyond the Original Scope}

The project expanded beyond its original scope in several areas. These additions strengthened the final system by extending it from a still-image redaction workflow into a broader tool for detecting and anonymizing different types of sensitive visual information. At the same time, several of these additions introduced new complexity and were not developed to the same level of maturity as the core image workflow.

\begin{itemize}
    \item \textbf{Video Support:} The original scope was limited to still images, but the system was later extended with video support as discussed in Section~\ref{sec:video_imp}. This demonstrated that the same detection and review principles could be applied to moving visual media. However, video also introduced challenges related to temporal consistency, processing time, tracking accuracy, and redaction stability across frames. The video workflow should therefore be understood as a valuable extension, but not as mature as the still-image workflow.

    \medskip

    \item \textbf{\Gls{inpainting} as a Redaction Method:} The initial redaction workflow used direct \gls{anonymization} methods such as \gls{masking}, blurring, and pixelation. \Gls{inpainting} was later explored as an additional method for replacing selected regions with generated background content. While this can improve visual appearance, it may also require more processing resources and must still be evaluated according to whether it reliably removes sensitive information. Due to its lower priority, as shown in Section~\ref{sec:priority}, the functionality was addressed later in the project when time was limited. Nevertheless, it produced acceptable results and was retained, as it was also requested by Safe Media AI, as shown in Appendix~\ref{app:meeting-2026-04-22}.

    \medskip

    \item \textbf{Market and Needs Mapping:} Beyond technical implementation, the project included mapping of market needs and existing redaction workflows. Input from real users, including users who work with images in practical settings, provided meaningful insight into existing redaction needs, system speed, and expectations for user control. This helped clarify the practical relevance of \gls{SafeVision} and supported the decision to combine automated detection with user-controlled review.

    \medskip

    \item \textbf{Custom Detection of Barcodes, QR Codes, and License Plates:} 
    Based on the definition of sensitive information established in Chapter~\ref{chap:theoretical_foundation}, the detection scope was expanded beyond faces and visible text to include barcodes, QR codes, and license plates. These elements were considered relevant because they may function as indirect identifiers or link to traceable information. Custom detection models were therefore developed and integrated for these categories, strengthening \gls{SafeVision}’s ability to detect sensitive content beyond the most obvious visual identifiers. This was an important technical achievement, but it also showed how dependent model development is on dataset availability, licensing, training time, and realistic evaluation data.

    \medskip

    \item \textbf{NER-Based Text Classification:} The text pipeline was extended beyond \acrshort{ocr} by adding named entity recognition classification for extracted text. This allowed the system to distinguish between general text and potentially sensitive entities. However, the results also showed that this was difficult to make reliable in realistic \acrshort{ocr}-based document scenarios. The \acrshort{ner} work should therefore be viewed as a useful extension of the text pipeline, but also as an area that would require more realistic data and further evaluation before it could be relied on as a primary privacy safeguard, as analyzed in Section~\ref{sec:ner_results}.
\end{itemize}

The additions beyond the original scope strengthened the project by showing that \gls{SafeVision} can be extended in several directions. They also created a broader and more complex system than originally planned. This was valuable for exploration, but it meant that some areas, especially video processing, \gls{inpainting}, and text classification, remained less refined than the core image workflow. The project therefore achieved more than initially planned, while also showing the importance of limiting scope when working with \acrshort{ml} based privacy systems.

\section{Group Reflection}

As described in Chapter~\ref{chap:devprocess}, the group followed a structured working rhythm with sprint planning, regular coordination meetings, task tracking, and clear role distribution. These routines gave the group a useful framework for collaboration, especially because \gls{SafeVision} consisted of several parallel work areas, including research, \acrshort{ml}, frontend development, backend development, testing, and report writing. In practice, this structure helped reduce confusion and made it easier to see who was responsible for different parts of the project.

A significant challenge was that the group had no prior experience with frontend development. React, TypeScript, and the structure of a larger frontend application were mostly new to the group at the start of the project. This created a steep learning curve, especially when implementing state management, component structure, user interaction, and backend communication. As a result, development time was spent learning unfamiliar technologies, restructuring code, and revisiting earlier frontend decisions that could have been handled more efficiently with more prior experience. At the same time, working through these challenges gave the group valuable practical experience and a better understanding of how frontend architecture affects usability, maintainability, and integration with the rest of the system.

However, the project also showed that structure alone does not guarantee effective progress. Although the group had defined responsibilities, some tasks became more complex and time consuming than expected, particularly model training, video processing, and integration of \acrshort{ml} components. This made it necessary for group members to support each other across their original roles. In retrospect, this flexibility was one of the group’s strengths, because it prevented the project from becoming too dependent on individual members and helped maintain progress during demanding periods.

The group learned that agile routines and role distribution are useful tools for coordination, but they are not sufficient on their own. Their value depends on how actively they are used to expose uncertainty, adjust priorities, and support collaboration. A key lesson from the project is that clear responsibilities create structure, while shared ownership and flexibility are necessary when working on a complex system where technical dependencies change over time.

\section{Technical Limitations and Challenges}
\label{sec:technical_limitations_and_challenges}

Although \gls{SafeVision} achieved its main goals, the project revealed several technical limitations. One important constraint was the need to use technologies, datasets, and models that were both free and compatible with commercial use. This influenced the model choices discussed in Section~\ref{sec:model_and_technology_choices_in_safeVision}. This restricted the range of candidate tools and models that could be considered for integration. As a result, some relevant alternatives were excluded due to licensing limitations rather than technical suitability alone.

Training custom models also proved demanding. Model training was performed on the group’s own machines, and in some cases the training process terminated due to out of memory errors, even on systems with 32 GB of RAM. These constraints may have limited further model improvement, for example through longer
training, larger configurations, or higher input resolutions.

Text classification was also a significant challenge. Although the \acrshort{ner} model achieved very high scores on the constructed test split, further evaluation showed that it was less reliable in real-world document scenarios, especially for person names, organizations, and locations (Section~\ref{sec:ner_results}). One reason was the lack of suitable datasets: few freely available resources matched the project’s privacy related categories, \acrshort{ocr} based document inputs, and licensing requirements at the same time. As a result, much of the training data had to be synthetic or adapted from external datasets, and the final system used the \acrshort{ner} model only as one part of a hybrid text-analysis pipeline.

Automatic detection itself cannot guaranty complete \gls{anonymization}. Section~\ref{sec:custom_trained_detection_models} illustrated that the system may produce \gls{false positive}s, where non-sensitive regions are detected, or \gls{false negative}s, where sensitive information is missed. This is especially important
when sensitive information appears as contextual details rather than clearly defined object categories. A sign, document, barcode, or background detail may be sensitive in one situation but harmless in another.

Video processing introduced additional challenges that were not present in the image workflow. In the current implementation, video support largely uses the processing pipeline on individual frames, combined with Kalman-based prediction between detection frames. This made it possible to extend the system beyond images, but it also means that the video workflow is not based on a dedicated video specific detection or tracking
architecture. The results indicate that this approach can keep \gls{bounding box}es present between detection frames and reduce processing time, but they do not prove that every predicted box remains correctly placed throughout the video. A stronger evaluation would require human-labeled ground truth for tracking, with measures such as \acrshort{iou}, recall, and \gls{false positive}s across multiple videos.

A related limitation is the trade-off introduced by the
\texttt{detect\_every} parameter. Higher values make video processing faster because detection runs less frequently, but they also increase the risk that short-lived objects are detected late or missed entirely. Kalman-based prediction can only continue regions that have already been detected and cannot
replace the detection step itself.

Another limitation was found when using Kalman-based prediction for manually created boxes in video processing. When a user draws a manual box, the system only has one initial position for the object and no movement history to estimate its direction or speed. This made it difficult for the Kalman predictor to determine where the object should move in the following frames. As a result, manual tracking was explored as an additional solution for cases where automatic prediction from a single user-defined box was not reliable enough. This manual tracking path primarily uses TrackerViT, with CSRT available as a fallback, but it still depends on visual continuity in the selected region. Manual tracking improved control in the tested car example illustrated in Figure~\ref{fig:manual_tracking_examples}, but it also had limitations, as it produced a \gls{false positive} after the car had left the scene. This shows that tracking can help follow selected objects while they are visible, but user review remains important when objects leave the frame, become occluded, move unexpectedly, or blend into the background.

Redaction precision is another limitation. Bounding-box-based redaction is simple and reliable, but it may cover more of the image than necessary. \Gls{segmentation} and \gls{inpainting} can produce more visually refined results (Figure ~\ref{fig:segmentation_comparison}), but they also introduce additional complexity and may not always be suitable for privacy-critical redaction. In a privacy oriented system, the redaction method must prioritize reliable \gls{anonymization} over visual appearance. For video, this is even more challenging, since frame-by-frame redaction may introduce flickering, unstable masks, or inconsistent visual results across consecutive frames.

Most of these challenges were originally lower prioritized as explained in Section~\ref{sec:priority}. \gls{SafeVision} involves a trade-off between detection coverage, redaction quality, and processing efficiency. These limitations do not remove the value of the system, but they show that practical privacy-preserving visual processing remains technically challenging even when the overall workflow is functional. 


\section{Future Development Opportunities}

Future development should prioritize components that were either outside the final scope or only partially developed, particularly video redaction, text analysis, deployment efficiency, and manual editing tools.

Video support was added beyond the original scope, and the system includes backtracking to reduce jitter and improve consistency between frames. As shown in Chapter~\ref{user_interface_and_usability}, users can also control the video detection rate, which affects how frequently detections are performed. Although these mechanisms improve stability, they do not fully solve temporal consistency. Since the current implementation largely reuses the image pipeline frame by frame, future work could investigate more dedicated video-specific methods for detection and tracking. This would also improve redaction method for video.

Manual tracking could also be improved. Future versions could include better stop criteria, uncertainty indicators, and keyframe correction. A user could correct the box on selected frames, and the system could then update or re-run tracking between those corrected frames. 

Support for more specialized sensitive content could also be expanded. For example, PDF417 codes on flight tickets were considered during the project, but creating a dedicated dataset for this narrow use case was too time-consuming relative to the broader value of detecting common barcode and QR code formats. Future work could extend the detection categories to include PDF417 codes, identity documents, tickets, forms, and other domain-specific identifiers.

Text classification should also be improved in future work. The results showed that the current approach was less reliable in real-world document scenarios than in the constructed evaluation setting, especially for categories such as person names, organizations, and locations (Subsection~\ref{sec:ner_results}). Future work could therefore focus on collecting more realistic datasets and refining the hybrid text-analysis pipeline for practical document inputs.
 
The existing solution strips the metadata, but preserving it is another possible extension. As explored in Appendix~\ref{app:metadata-handling}, metadata may be relevant in workflows where authenticity, traceability, documentation, or auditability must be preserved after redaction. This was not included in the final system because the project centered on visual detection and redaction rather than file metadata handling. Future work could investigate how metadata should be preserved, removed, or modified depending on privacy and documentation requirements.

The redaction workflow could also be expanded with more flexible manual editing tools. User testing from Section~\ref{sec:user-testing} indicated that users may need more control when sensitive regions do not fit rectangular \gls{bounding box}es or when automatic detections require correction. Future versions could therefore include improved manual highlighting controls such as shapes or a snippet tool to refine the bounding areas.
 
Performance and deployment optimization should also be considered. Section~\ref{sec:performance_tests} presented benchmarks comparing CPU-based execution, \gls{gpu}-based execution, and a cloud-based backend. Future versions could benefit from \gls{gpu} deployment, model optimization, asynchronous batch processing, and more selective use of expensive components such as \gls{segmentation} and \gls{inpainting}. This would be especially relevant for larger files, video processing, and high-volume organizational workflows.

External feedback from market-oriented meetings Appendix~\ref{app:meeting-2026-03-12} and user tests Appendix~\ref{appsec:finale_real_test} pointed to several possible future implementation improvements. Feedback identified improvements that could make the workflow more suitable for real use, such as clearer progress feedback during redaction, better explanation of terminology, optional Norwegian language support, and a simple FAQ or help page. These points are not primarily about changing the detection models, but about improving usability, workflow transparency, and user confidence during processing.

Further evaluation with real users and larger datasets would also be valuable as a separate future activity. This would make it possible to assess how well the hybrid workflow performs in practical redaction scenarios and whether the balance between automation, privacy, and user control should be adjusted. Future user testing could also provide broader insight into how sensitive information is interpreted in different contexts and help improve detection overall.

\section{Ethical Dimensions}

The \gls{SafeVision} system was developed to detect and redact sensitive information in images and videos. Visual media may contain direct identifiers, but also indirect identifiers, or contextual details, as discussed in Section~\ref{sec:sensitive_information_in_vm}. This makes privacy protection in visual media challenging, since media that appears anonymized may still reveal more information than intended if relevant context remains visible.

As mentioned in Section~\ref{sec:technical_limitations_and_challenges} automated solution does not only propose a technical, but an ethical problem as well. Automated \gls{anonymization} cannot guarantee complete privacy protection in all situations. Detection models may miss relevant regions, tracking may flicker, classify regions incorrectly, or produce results that require further human judgment. In addition, redaction methods do not necessarily result in full \gls{anonymization} if the environment still makes a person or location identifiable. \gls{SafeVision} should therefore be understood as a privacy supporting tool rather than a guarantee that all sensitive information has been removed. Therefore, user control was retained as an important part of the system design. 

Another ethical dimension concerns the resources required to improve and maintain the system over time. Better detection models and more powerful hardware could improve accuracy and reduce the risk of missed sensitive information, but they may also increase electricity consumption, infrastructure costs, and maintenance work as discussed in Section~\ref{sec:susaf_dimensions}. This creates a trade-off between improving privacy protection and using more computational, economic, and human resources. From an ethical perspective, future development should therefore consider whether technical improvements provide enough practical value to justify their environmental and organizational costs. \gls{SafeVision} should not only aim to become more accurate, but also remain sustainable, maintainable, and realistic for the organizations expected to use it.

The ethical value of \gls{SafeVision} therefore depends not only on model accuracy, but also on careful system design, clear communication of limitations, responsible resource use, and human oversight during the final review of results. The system can reduce manual workload and support more consistent redaction, but it should be used with awareness of both its technical limitations and its long-term operational costs. A final user review remains necessary before anonymized media is shared or published.

\section{Reflection of Use of Artificial Intelligence}
\label{sec:reflection-ai-use}

The use of artificial intelligence tools during the project was helpful, but the usefulness varied depending on the task. For smaller and more clearly defined problems, AI tools often saved time, especially in the tasks described in Section~\ref{sec:ai-development-tool}. AI worked well as a support tool in these cases because the problems were limited in scope and the suggested outputs could be checked quickly.

AI was less useful for complex programming and debugging tasks, especially when problems depended on project specific context or missing details in the prompt. In these cases, the group sometimes spent too much time going back and forth without reaching a working solution. Some generated code was also unsuitable because it was unnecessarily complicated, or solved a slightly different problem. In retrospect, complex issues were often better handled through direct code inspection, debugging tools, or group discussion, and that AI suggestions should not be treated as ready made solutions.

Using AI in report work also had limitations. Some suggestions made the text longer than necessary. This was especially important when describing technical implementation details, since small changes in wording could make the report less accurate. The group therefore had to review and simplify reformulated AI-generated text carefully to ensure that the final writing remained precise and consistent with the actual work carried out in the project.

The main lesson from using AI in the project is that it can be valuable as a support tool, but it does not remove the need for technical understanding. It was most useful when used for narrow, verifiable tasks, and less reliable when used for open ended debugging or larger code changes. In future projects, the group would use AI more deliberately by limiting it to tasks where the output can be checked quickly, while relying more on direct debugging, testing, and group discussion for complex implementation problems.

\section{Project Reflection}

An important lesson concerns the research phase. Early in the project, the group spent considerable effort on finding usable models, comparing technologies, and integrating them into the prototype. However, the scope of what should be considered sensitive information in visual media was not fully established before some implementation decisions were made. Chapter~\ref{chap:theoretical_foundation} later showed that this definition is broader than faces and visible text, and also includes indirect identifiers such as license plates, barcodes, QR codes, signs, and contextual visual details. A more structured research phase at the beginning could have clarified the detection scope earlier and made it easier to prioritize datasets, model training, and custom object categories.

User testing and interface improvements provided useful feedback, as described in Section~\ref{sec:user-testing}, however some of this effort could have been balanced more carefully. More time could have been allocated to dataset development, model improvement, PDF417 detection, and video tracking. Video support expanded the project beyond the original image based scope, but the added complexity of tracking, temporal consistency, and performance meant that the video workflow did not reach the same maturity as the still image workflow. Since the core contribution of the project was a system for \acrshort{ml} based detection and redaction, these areas could have further strengthened the technical contribution.

A key takeaway from the project is that technical implementation and problem understanding must develop together. Future projects of a similar type would benefit from spending more time early on defining the problem space, validating priorities with stakeholders, and deciding which technical areas should receive the most development effort. A clearer early research and prioritization phase could have made the development process more structured, reduced the need to revisit implementation decisions later in the project, and allowed more time for areas that could be improved.
